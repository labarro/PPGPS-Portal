## Objetivo

App Next.js + Payload rodando em ambientes isolados, com pipeline de migrations, qualidade e controles básicos de segurança.

## Incluído (escopo fechado)

- Projeto base Next.js (App Router, TypeScript strict) com Payload 3 em `src/app/(payload)` e `src/app/(site)`; pnpm; `.nvmrc`; `engines`.
- `@payloadcms/db-postgres`; `docker-compose.yml` com Postgres e MinIO; scripts `db:up`, `migrate`, `migrate:create`, `migrate:status`, `generate:types`, `seed`, `dev`, `lint`, `typecheck`, `test`, `test:e2e`, `build`.
- Coleções **mínimas** `users` (auth padrão) e `media` (upload básico).
- Localização: pt-BR padrão; `en` declarado e oculto na UI pública.
- Página pública provisória em `(site)`.
- ESLint, Prettier, Husky, lint-staged, Commitlint; Vitest e Playwright com testes de fumaça.
- CI (GitHub Actions): lint, typecheck, unit, integração (Postgres de serviço), E2E, build, gitleaks, `pnpm audit`; **job de verificação de migrations** (banco limpo, *drift*, `down`/`up`).
- Neon: branches `main`, `staging`, `seed`; workflow de branch efêmero por PR (cria de `seed`, migra, remove ao fechar).
- Vercel: deploy automático de produção **desativado**; previews por PR apontando para o branch efêmero; deploys de homologação e produção disparados pelo pipeline.
- Middleware de autenticação básica + `X-Robots-Tag: noindex` fora da produção.
- GraphQL e playground desabilitados; cabeçalhos básicos (HSTS, `nosniff`, `Referrer-Policy`, `frame-ancestors`).
- Renovate ou Dependabot; segredos distintos por ambiente; `.env.example` sem valores.
- `README.md` com setup reproduzível.
- ADRs: **versões fixadas** (Next/Payload/React/Node) e **mecanismo de detecção de *drift*** (e deploy controlado pela Vercel, se decidido).

## Fora de escopo (explicitamente)

- Campos `roles`/`active`, RBAC, auditoria, convites, recuperação de senha, limites de taxa (S02)
- Storage R2 com validação de upload, coleção `documents`, campos `alt/credit/license` (S02)
- Tailwind/shadcn, layout público, globals `Navigation`/`Footer`/`SiteSettings` (S02)
- Sentry, CSP, e-mail, backup (S02)
- Qualquer coleção de domínio (`research-lines`, `people` etc.) ou global `GroupProfile` (S03+)
- Domínio público e remoção de `noindex` da produção (S06)

## Histórias de usuário

- Como desenvolvedor, quero subir o ambiente com um comando, para começar a trabalhar sem configuração manual.
- Como supervisor, quero um preview isolado por PR, para revisar cada entrega sem afetar a homologação.
- Como responsável técnico, quero que migrations nunca rodem durante o build e que divergências de schema quebrem o CI.

## Tarefas técnicas

1. Inicializar a partir do template oficial do Payload com Next.js; fixar versões em ADR.
2. Configurar adaptador Postgres, `docker-compose.yml`, scripts e primeira migration.
3. Criar `users` e `media` mínimas; gerar e versionar `payload-types.ts`.
4. Configurar localização (pt-BR/en).
5. Configurar qualidade (ESLint, Prettier, Husky, lint-staged, Commitlint, `tsc --noEmit`).
6. Configurar Vitest (integração inicializa Payload e cria usuário) e Playwright (home e login no admin).
7. Workflows: `ci.yml`, `migrations-check.yml`, `preview-db.yml`, `deploy-staging.yml`, `deploy-production.yml` (aprovação manual), conforme seção 28.1.
8. Middleware de autenticação básica/`noindex` por variável de ambiente; cabeçalhos básicos em `next.config`.
9. Desabilitar GraphQL; garantir `/api/graphql` → 404.
10. Documentar setup no `README.md` e sincronizar comandos com `AGENTS.md` §3.

## Modelagem afetada

`users` (mínimo, auth padrão do Payload) e `media` (mínimo). Ver seção 13.6.

## Controles progressivos (seção 17.7 — S01)

Segurança: cabeçalhos básicos, GraphQL desabilitado, gitleaks e `pnpm audit` no CI, Renovate/Dependabot, segredos por ambiente, ambientes não produtivos com autenticação básica e `noindex`. Privacidade: `.env` fora do git; fixtures fictícias. Qualidade: TS strict, lint, Vitest, Playwright, CI obrigatório, verificação de migrations.

## Critérios de aceite

- [ ] `pnpm install && pnpm db:up && pnpm migrate && pnpm dev` funciona em máquina limpa seguindo o README
- [ ] `/admin` permite criar o primeiro usuário admin e fazer login
- [ ] Um PR com alteração de schema **sem** migration correspondente falha no CI
- [ ] Dois PRs abertos simultaneamente usam bancos distintos (branches efêmeros) e o branch é removido ao fechar o PR
- [ ] `next build` não executa migrations; a migration roda em job separado com trava de concorrência
- [ ] Homologação e previews exigem autenticação básica e respondem com `noindex`; `/api/graphql` retorna 404

## Testes necessários

Fumaça E2E (home e login no admin); integração que inicializa o Payload e cria um usuário; teste do job de migrations (PR de prova com schema sem migration).

## Roteiro de homologação (supervisor)

1. Clonar o repositório em máquina limpa e seguir o README até `pnpm dev`.
2. Acessar `/admin`, criar o primeiro admin, sair e entrar novamente.
3. Abrir PR de teste alterando um campo sem gerar migration → confirmar falha no CI; gerar a migration → CI verde.
4. Abrir dois PRs simultâneos e conferir no painel do Neon os dois branches efêmeros; fechar um e verificar a remoção.
5. Acessar preview e homologação sem credenciais (esperado 401) e com credenciais; conferir `X-Robots-Tag: noindex` e 404 em `/api/graphql`.
6. Conferir nos logs do deploy que `next build` não roda migrations e que o job de migrate usa `concurrency`.
7. Conferir que o deploy automático de produção está desativado na Vercel.

## Riscos e pontos de atenção

- Compatibilidade Next/Payload: usar a combinação do template oficial.
- Limite de 10 branches no Neon Free: limitar previews simultâneos (4–5).
- Deploy controlado pelo pipeline na Vercel: validar nesta sprint e registrar em ADR.
- Confirmar se migrations do Payload rodam em transação (premissa da seção 24.6).

## Definition of Done

DoD global (`AGENTS.md` §12) + README de setup validado pelo supervisor em sua máquina.
